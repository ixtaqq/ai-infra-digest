## Problem Statement

The roadmap listed "Price Threshold Alerts — user-defined ticker price targets trigger instant Telegram notifications." As designed, that phrasing implies real-time, actionable trading alerts. The actual validated need is much narrower: a passive, once-daily "NVDA crossed $130" awareness ping that supports an existing habit of checking prices to maintain a mental model of the market — not a trading trigger.

## Demand Evidence

Weaker than Thesis Evolution's dated incident, and explicitly acknowledged as such:

- First answer: "I check prices manually and it's annoying" — a real, recurring behavior, not hypothetical.
- Pushed on what decision the check serves: *"I check because I'm maintaining a mental model of the market, not because a trade decision is pending right now. It's an awareness habit, not an execution trigger."*
- No dated incident, no specific missed decision, no "I was upset when I found out too late" moment — this is closer to a mild, ambient habit than acute pain.
- The independent outside-voice review flagged this explicitly: evidence here is "an order of magnitude weaker" than Thesis Evolution's validated incident, and recommended timeboxing this as an experiment rather than committing to it as a permanent feature.
- **Founder decision: full commitment, no timebox** — proceeding despite the weaker evidence, with the scope narrowed to match what the evidence actually supports (informational, not actionable).

## Status Quo

Manually checking stock prices/digest content periodically (not tied to a specific pending decision) to keep a mental model of where tracked tickers stand.

## Target User & Narrowest Wedge

Same as Thesis Evolution and every other Phase X/XI item so far: the founder, pre-product, single user. Narrowest wedge: a single daily comparison of tagged tickers against price data the pipeline already fetches, firing one Telegram message when a threshold is crossed.

## Constraints

- Solo maintainer, `<$1/month` AI budget (this feature has zero AI cost — pure data comparison)
- Prices are only fetched once per day inside the existing `generateDigest()` → `fetchStockPrices()` call (shared across all users) — there is no separate real-time price-polling infrastructure, and this design does not add one
- `fetchStockPrices(tickers)` (`src/utils/stocks.ts:104`) only fetches prices for the tickers it's given. Today that list (`allTickers`, `src/index.ts:317-325`) is built from tickers mentioned in that day's collected articles plus the derived top-stocks list — **a watched ticker with no article mention that day is not in this list today.** This design requires unioning all active `price_watches.ticker` values into `allTickers` before the fetch call, or a watched ticker would never get priced and its watch would silently never fire. This union is now a required part of the implementation, not an optional nice-to-have (see Dependencies).
- `generateDigest()` runs once and produces a single shared `GeneratedDigest`/`stockPrices` map; per-user delivery happens separately via the fan-out loop that sends to each `chat_id` (around `src/index.ts:613-664`). Watch-checking must happen in that per-user fan-out, keyed by `chat_id`, not inside the single shared `generateDigest()` call — otherwise there's no natural place to know which user to notify.
- `/alert` is already a registered Telegram command for an unrelated system (impact-score article alerts: `/alert on`, `/alert off`, `/alert threshold N`) — must not collide. Confirmed `/watch` is free (not in the registered command list).

## Premises

1. The right problem is narrower than the roadmap phrase implied: an informational awareness ping, not an actionable trading trigger. **Agreed.**
2. "Instant notifications" (original roadmap wording) is technically inaccurate for this architecture — checks happen once daily when `generateDigest()` runs, not in real time. **Agreed.**
3. Existing code reuse: `fetchStockPrices()` already fetches daily price + % change for every mentioned ticker; the threshold check is a comparison against data already being fetched. **Agreed.**
4. Naming collision to avoid: needs a distinct command from `/alert`. **Agreed** — command is `/watch` (see Recommended Approach).
5. New storage needed: per-user, per-ticker thresholds need a new table, not an extension of an existing global one. **Agreed** — and re-confirmed after the outside voice challenged it (see Cross-Model Perspective); a dedicated table matches every other per-entity write pattern already in this codebase and isn't premature here.

## Approaches Considered

### Approach A: Minimal — one-shot fire-then-clear (SELECTED)
New `price_watches` table (`chat_id, ticker, threshold, direction, created_at`). On `/watch TICKER PRICE`, the current price is fetched synchronously to infer direction; if it can't be fetched, the command fails with an error rather than storing an ambiguous watch. Before the daily `fetchStockPrices()` call, all distinct active `price_watches.ticker` values are unioned into `allTickers` so watched tickers are always priced, even with zero article mentions that day. The threshold check happens in the per-user delivery fan-out (keyed by `chat_id`), not inside the single shared `generateDigest()` call. On trigger: send the Telegram message first, then delete the row only after a confirmed successful send — if delete fails after a successful send, the watch may re-fire next run (a duplicate, safe) rather than risk deleting first and silently losing the notification. Commands: `/watch NVDA 130`, `/watch NVDA off`, `/watch list`. Fires once per threshold cross, then the row is deleted — no re-arming, no history.
Effort: S · Risk: Low · Reuses: existing `fetchStockPrices()` output (extended with watched tickers), the per-user delivery fan-out loop, `supabaseFetch()` patterns.

### Approach B: Durable — re-armable + history
Same schema plus a `triggered_at` timestamp instead of deleting on fire, so a watch can re-arm if price crosses back, and a `/watch history` command shows past triggers.
Effort: M · Risk: Low-Med (more edge cases: re-arm threshold logic, history pruning).

### Approach C: Unified watch-condition system
Generalize `/alert` (impact-score) and this new price-watch into one `watch_conditions` table with a `type` column, so future condition types (sentiment, filing-based) plug into the same system.
Effort: L · Risk: Medium — touches the existing, working `/alert` system for a benefit that's speculative until more condition types actually exist. Not recommended given the weak-evidence context here.

## Recommended Approach

Approach A. Matches the narrowed, informational scope exactly, has the smallest blast radius (new table, zero changes to existing `/alert`), and the founder's own choice given weaker demand evidence is to build the minimal real version, not the durable one — Approach B's re-arm/history complexity isn't justified until Approach A proves it gets used at all.

## Open Questions

- Does a fired watch need any confirmation beyond the Telegram message itself (e.g. should `/watch list` show recently-fired-and-cleared watches for a day)? Default: no — matches the deliberately minimal, no-history scope.
- Should there be a cap on how many watches one user can have active at once? Default: no cap for now — solo user, trivial volume, revisit only if this becomes multi-user.
- What direction does a watch get if the current price exactly equals the threshold at creation time? Default: `above` (arbitrary but deterministic — document this in code, not just here).
- What happens to the once-daily `fetchStockPrices()` call cost/rate-limits as more distinct watched tickers accumulate beyond what articles already cover? Default: no cap for now, same reasoning as the watch-count question above — revisit if this ever stops being a single user.

## Success Criteria

- A threshold set via `/watch TICKER PRICE` correctly fires exactly one Telegram message the next time `generateDigest()` runs after the price crosses it, and the watch is cleared afterward.
- Zero regressions to the existing `/alert` command (impact-score alerts) — fully separate table, fully separate command name.
- The founder actually uses this for at least a few real tickers over the following weeks (the informal test the outside voice proposed, even though the founder chose full commitment over a formal timebox).

## Distribution Plan

No new channel — ships inside the existing Telegram bot and the existing daily digest generation cadence, both already deployed.

- `src/index.ts:317-325` — `allTickers` construction must be extended to union in all distinct active `price_watches.ticker` values before `fetchStockPrices()` is called, or watched tickers with no article mention that day are never priced (this was the fatal gap caught in adversarial review — see below)
- `src/index.ts:613-664` (per-user delivery fan-out) — threshold-check-and-notify logic lives here, keyed by `chat_id`, reading against the shared `stockPrices` map already produced upstream; send-then-delete ordering on trigger
- `src/utils/supabase.ts` — new CRUD methods for `price_watches` (insert, list-by-chat, delete-by-id, distinct-active-tickers query)

## Adversarial Review Notes

A fresh reviewer subagent (no conversation context) read this doc cold against the actual codebase and found one fatal flaw and one real architectural gap before any fixes were applied:

1. **Fatal (fixed above)**: the doc's original premise — that `fetchStockPrices()` "already fetches daily price + % change for every mentioned ticker" — is true but was being misapplied. A *watched* ticker is, by definition, one the user may care about independent of whether an article mentions it that day. As originally written, Approach A would have silently never fired for any ticker absent from that day's articles. Fixed by requiring the `allTickers` union described in Dependencies.
2. **Real gap (fixed above)**: "checked inside `generateDigest()`" was imprecise — `generateDigest()` produces one shared result with no per-`chat_id` loop; that loop lives in the delivery fan-out. Fixed by relocating the check to the fan-out and specifying send-then-delete ordering explicitly.
3. Minor: an earlier draft claimed reuse of "`/watchlist`-style command parsing already in `src/index.ts`" — no such command exists (watchlist is a preference field, not a parsed command.) Removed the false claim.
