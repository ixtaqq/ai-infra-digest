## Overview

`/watch TICKER PRICE` lets a user set a one-shot informational price threshold on any ticker. Checked once daily inside the existing digest-generation cycle (no new polling infrastructure), fires exactly one Telegram notification when crossed, then clears itself.

## Architecture

```
generateDigest()                                    (runs once per scheduler tick)
  │
  ├─ supabase.getAllPriceWatches() ─────────────┐    ONE query, not one per user
  │                                             │
  ├─ allTickers = [...watchedTickers,           │    watched tickers FIRST — survive
  │                ...articleTickers,           │    the fetchStockPrices 25-ticker
  │                ...topStockTickers]          │    .slice(0,25) truncation
  │       (deduped, capped at 25)               │
  │                                             │
  ├─ fetchStockPrices(allTickers) → stockPrices │
  │                                             │
  └─ GeneratedDigest { ..., stockPrices,        │
                       activeWatches } ◄────────┘    threaded through, not refetched

scheduler.ts fan-out loop (src/scheduler.ts:147-160, NOT src/index.ts —
deliverDigest() itself only ever handles one chat_id per call)
  │
  └─ deliverDigest(generated, user.chat_id, user)   (src/index.ts:613-700)
        │
        ├─ send digest (existing)
        ├─ if targetChatId defined:
        │     myWatches = activeWatches.filter(w ⇒ w.chat_id === targetChatId)
        │     triggered = myWatches.filter(w ⇒ isTriggered(w, stockPrices))
        │     if triggered.length:
        │        send ONE combined "🔔 Price Watch" message
        │        on confirmed success → deletePriceWatches(triggered.map(w ⇒ w.id))
        └─ (runPipeline()'s legacy call, targetChatId undefined → watch logic skipped)
```

Two corrections to the design doc's own file/line citations, found during review and confirmed by an independent outside-voice pass against the real code:
- The design doc's "`src/index.ts:613-664`, the fan-out loop" is imprecise — that range is `deliverDigest()`'s single-call body. The actual loop over users is `src/scheduler.ts:147-160`. This doesn't change the implementation (filtering by `targetChatId` still happens correctly inside `deliverDigest()`, called once per user by that loop) — it just means don't go looking for a `for` loop in `index.ts`.
- `fetchStockPrices()` truncates to 25 tickers (`src/utils/stocks.ts:109`, `.slice(0, 25)`) **after** the union — a bug the adversarial review on the design doc didn't catch. Watched tickers must be prepended, not appended, or they get silently truncated whenever the day's article tickers alone approach 25.

## Schema

```sql
CREATE TABLE IF NOT EXISTS price_watches (
  id BIGSERIAL PRIMARY KEY,
  chat_id BIGINT NOT NULL,
  ticker TEXT NOT NULL,
  threshold DOUBLE PRECISION NOT NULL,
  direction TEXT NOT NULL CHECK (direction IN ('above', 'below')),
  created_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(chat_id, ticker)
);

CREATE INDEX IF NOT EXISTS idx_price_watches_chat_ticker ON price_watches(chat_id, ticker);

ALTER TABLE price_watches ENABLE ROW LEVEL SECURITY;
CREATE POLICY "service_role_full_access" ON price_watches
  FOR ALL TO service_role USING (true) WITH CHECK (true);
-- No public_read policy — this is per-user private data (matches
-- user_preferences/user_delivery_log, NOT ticker_thesis_history/sec_filings).
```

`UNIQUE(chat_id, ticker)` means re-setting a watch on a ticker the user is already watching upserts (via `on_conflict=chat_id,ticker`, the same idiom already used for `ticker_theses`) rather than erroring or duplicating.

## Direction / Trigger Formulas

New pure-function module `src/utils/price-watch.ts` (no I/O, directly unit-testable):

```typescript
export function inferDirection(threshold: number, priceAtCreation: number): "above" | "below" {
  return threshold >= priceAtCreation ? "above" : "below";
}

export function isTriggered(watch: { direction: "above" | "below"; threshold: number }, currentPrice: number): boolean {
  return watch.direction === "above" ? currentPrice >= watch.threshold : currentPrice <= watch.threshold;
}
```

## Command Grammar (`/watch`, registered in src/index.ts)

| Input | Behavior |
|---|---|
| `/watch` | Usage + current list (same as `/watch list`) |
| `/watch list` | List active watches for this chat_id |
| `/watch NVDA 130` | Set/replace a watch on NVDA at 130 (synchronous price lookup infers direction; fails closed if the lookup fails) |
| `/watch NVDA off` | Clear the NVDA watch for this chat_id |
| `/watch NVDA` (no 2nd arg) | Usage error |
| `/watch NVDA abc` / `-5` / `0` | Usage error — must be a positive number |

- Ticker not restricted to the curated `TICKER_MAP` — same ≤5-char-symbol acceptance as `fetchStockPrices`, validated by the synchronous lookup itself.
- `escapeHtml()` applied to the ticker in every response message, matching existing HTML-escaping discipline.
- The synchronous price lookup at `/watch` creation time is wrapped in a `Promise.race()` against an ~8s timeout (new, local to the handler — does not modify the shared `fetchPrice()`/`fetchStockPrices()` used by the batch path) so a slow/hanging Yahoo response fails closed instead of hanging the Telegram command indefinitely. This is a pre-existing gap in shared code, newly exposed by calling it synchronously from an interactive handler for the first time.

## Performance Notes

- New query cost negligible — `getAllPriceWatches()` only runs when `generateDigest()` runs, which only happens when `scheduler.ts` already has pending users (not every 15-min tick).
- Plain `.filter()` per user in the fan-out is fine at this table's realistic size (solo user, low tens of rows) — no index/grouping structure needed yet.
- Zero AI/budget-gate interaction — pure data comparison, doesn't touch `isMonthlyBudgetExceeded()`.
- Accepted tradeoff (already deferred in the design doc, just reconfirmed): if watched tickers ever exceeded 25 on their own, article tickers would be the ones truncated instead. Non-issue at current solo-user scale.
