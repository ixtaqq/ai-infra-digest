## Problem Statement

The v10.1 Bull/Bear Thesis Snapshot feature generates a weekly bull_case/bear_case/confidence narrative per ticker, but `ticker_theses` has `UNIQUE(ticker)` — every Sunday's run destroys the previous week's row. There is no way to see whether a thesis is strengthening or weakening over time; the qualitative reasoning behind a shift (not just whether sentiment moved) is lost the moment the next snapshot lands.

## Demand Evidence

Specific, dated incident — not hypothetical:

> "Last Thursday (~2026-07-02), NVDA — I noticed the daily digest had been consistently bullish on NVDA for two weeks and wanted to see the trend: was it strengthening or weakening, especially after Blackwell delay news? I opened the dashboard, looked at ticker_theses, and realized only the latest snapshot exists. I had to manually scroll old Telegram messages to reconstruct the narrative. I was trying to decide whether to add more NVDA exposure, and without the trend I felt like I was guessing."

By contrast, the other two features originally bundled under "Phase X" have no such evidence:
- Catalyst Tracker: "I haven't missed a catalyst yet ... mild pain, not acute."
- Alerts (thesis change): "I've noticed shifts ... but not urgently enough to need a push notification."

**Decision: Catalyst Tracker and Alerts are cut from this design.** They ride on the same roadmap label as Thesis Evolution but have zero pain behind them. Building them now would be solving a problem nobody — including the founder — has actually hit yet.

## Status Quo

Manually scrolling old Telegram digest messages to reconstruct what the thesis used to say. Works, but doesn't scale past a week or two of memory, and costs real time at exactly the moment a real decision (position sizing) is being made.

## Target User & Narrowest Wedge

Honest answer to "who else needs this": **no one yet — it's for me.** Pre-product stage; the founder is the only validated user, making their own NVDA position-sizing decision. This is a legitimate founder-market-fit-of-one build (plenty of real products start this way), but it means the design must stay scoped to what the founder actually does, not a hypothetical future multi-tenant dashboard user.

Narrowest wedge: can the founder answer "is my thesis on ticker X strengthening or weakening" without manual archaeology, using only the interfaces already opened during the week (Telegram, dashboard).

## Constraints

- Solo maintainer, `<$1/month` AI budget currently (see `AUDIT.md`, `README.md` Cost Estimate)
- Existing `ticker_theses` table and its consumers (`/thesis NVDA` command, dashboard Thesis Snapshots card) must not regress
- Weekly thesis-generation cadence (`scripts/run-weekly-thesis.ts`) already runs on GitHub Actions cron (Sunday 4 AM UTC) — any change should fit that cadence unless a cost/architecture decision says otherwise

## Approaches Considered

### Approach A: Sibling History Table + Telegram-only (minimal viable)
New `ticker_thesis_history` table (`ticker, bull_case, bear_case, confidence, key_drivers, week_of, created_at`; `UNIQUE(ticker, week_of)`), insert-only. `ticker_theses` is never touched — zero regression risk to the existing `/thesis NVDA` (latest) behavior or dashboard card. `generateTheses()` gets one extra insert alongside the existing `upsertTickerTheses()` call. `/thesis NVDA` extended to show the last 4-6 snapshots as plain chronological text.
Effort: S · Risk: Low · Reuses: `processor/thesis.ts`, `utils/supabase.ts` upsert patterns, `utils/escape.ts`, existing `/thesis` command handler in `src/index.ts`.

**Write semantics:** `week_of` is the same cron run date already used to key the weekly job (the Sunday 4 AM UTC run date). The two writes in `generateTheses()` — the existing `upsertTickerTheses()` call and the new history insert — are independent best-effort calls, same as the rest of this codebase's Supabase writes (see `utils/supabase.ts` patterns elsewhere): if one fails, log and continue rather than rolling back the other; no DB transaction. On a manual re-run for the same week (e.g. retry after a failed cron), the history insert uses `on_conflict=ticker,week_of` with `resolution=merge-duplicates` (the same pattern already used by `upsertTickerTheses()`), so a retry overwrites that week's history row instead of erroring or duplicating — this makes the history insert itself safely idempotent even if only it failed and is retried alone (e.g. `upsertTickerTheses()` succeeded but the history insert timed out mid-write).

**Ticker lifecycle:** history commands/queries show whatever snapshots exist for a ticker, down to a single row for a newly-tracked ticker — no special-casing required. De-tracked tickers keep their historical rows; nothing deletes them.

### Approach B: History Table + Dashboard Timeline Card (ideal architecture) — SELECTED
Same schema and backend as Approach A (sibling history table, zero risk to `ticker_theses`). Additionally extends the dashboard's Thesis Snapshots card (`website/dashboard/index.html`) to render a timeline of the last N weeks per ticker, with a computed confidence-delta line ("confidence: 7 → 8") between consecutive snapshots — computed client-side in the dashboard from the raw confidence values already returned by the history query; no schema change, no stored delta column, no new AI calls.
Effort: M · Risk: Low-Med · Reuses: same backend as A, plus the dashboard's existing Supabase-read/auto-refresh patterns.

**Real implementation risk (not just "more surface area"):** the current Thesis Snapshots card presumably renders one row per ticker (a single latest snapshot). A timeline view is a one-to-many render — ticker → N history rows — which is a genuine restructuring of that card's data-fetch and render logic, not a trivial extension. Confirm the card's existing fetch pattern before estimating Approach B's effort; if it's built assuming exactly one row per ticker, budget more than a small tweak.

### Approach C: Daily Cadence + Full Versioned Ledger (creative/lateral)
Move thesis generation from weekly to daily (piggyback the existing daily pipeline instead of a separate script); `ticker_theses` becomes a derived "latest" view over a daily history table. Day-level resolution instead of week-level — closer to catching a same-day reasoning shift. Cost: ~7x current thesis spend (~$0.01/week → ~$0.07/week, still trivial in absolute terms but a real cadence/cost decision).
Effort: L · Risk: Medium (touches pipeline cadence, budget gates, "latest" semantics) · Not recommended yet — over-scoped for a feature validated by one incident.

## Recommended Approach

Approach A was the recommendation (from both the independent second opinion and this analysis) on the grounds of smallest diff and zero blast radius for a feature validated by exactly one incident so far.

**The founder chose Approach B instead** — accepting the larger surface area (dashboard timeline card) in exchange for a visual view of the trend, not just Telegram text. This is a legitimate call once weighed against the tradeoffs (Approach B's backend is identical to A's — same table, same insert-only safety — the only added risk is dashboard-side, which is genuinely low since it's read-only Supabase queries into existing dashboard infrastructure).

**Build order to de-risk B:** do Approach A's backend work first (schema + insert + Telegram `/thesis` history text) as a real, shippable milestone — it validates the schema and generation logic end-to-end before any dashboard code is written. Then layer the dashboard timeline card on top as a second, separable step. This way if the dashboard piece slips or turns out not to be worth it, the Telegram-only version is still a complete, working feature on its own.

## Open Questions

Resolved with defaults so implementation isn't blocked — revisit only if real usage says otherwise:

- **Backfill**: None. Start clean from the next weekly run; scraping Telegram history to backfill is out of scope.
- **Snapshot count shown**: Default to the last 6 (roughly a quarter of weekly snapshots), no pagination in v1. Both `/thesis NVDA` and the dashboard card use the same default.
- **Confidence-delta visual treatment**: Plain text next to the number for v1 (e.g. "confidence: 7 → 8"), no color or arrow icon. Revisit only if it's genuinely hard to read once real data is in front of it.
- **`daily_derived_metrics` join**: Explicitly out of scope for this slice (see Premises #4) — not forgotten, deliberately deferred. Revisit only after the qualitative history has been used in a real decision and still leaves a "why" gap unanswered.

## Success Criteria

- Next time the founder has a "is my NVDA thesis holding up" moment, they can answer it from the `/thesis NVDA` command or the dashboard card in under 30 seconds, without touching Telegram message history.
- `ticker_theses` (latest-only) and its existing consumers show zero regressions after this ships.
- At least 2-3 real weekly snapshots have accumulated and been used by the founder in an actual decision before considering Approach C (daily cadence) or reviving Catalyst Tracker/Alerts.
